# managents helper

The program that runs on your computer: it finds open AI agent sessions and streams their status to every connected
managents display. One static binary, no runtime, no configuration. It also installs itself as a background service
and flashes the display's firmware, which is embedded in it.

## Install

Most people use the one-liner from the [README](../README.md#get-started). From a clone:

```bash
make install     # builds bin/managents, copies it to ~/.local/bin and runs `managents service install`
```

Or build only: `make helper` writes `bin/managents` (`go build ./cmd/managents` in this directory works too, but
then the binary has no firmware: `managents flash` needs `--image`).

## Commands

Bare `managents` prints the help. Every command takes `-h`.

| Command | What it does |
|---|---|
| `managents run [--port P] [--log-level L] [--log-file F] [--claude-context N]` | Stream to displays until Ctrl-C. This is what the service runs. Without `--port`, USB serial ports are scanned every 2 s and each candidate is identified with a `hello` handshake. `--log-file` appends the log to a file (past 1 MiB it moves to `F.1` at the next start). |
| `managents status [--json] [--watch] [--claude-context N]` | Print the detected sessions, or the exact frame that would be sent. Needs no display. The table has a FOLDER column with each session's working directory (`--json` has no paths). `--watch` repaints the table every 2 s until Ctrl-C, each frame replacing the last one; output that is not a terminal (a pipe, a file) gets one report, and `--json` cannot be combined with `--watch`. |
| `managents devices` | List the USB serial ports and say which are managents displays, with board and firmware version; a port in use by another program (the service) or a board that is not a display (new board? `managents flash`) says so. |
| `managents service install\|uninstall\|start\|stop\|status` | The background service, see [below](#the-background-service). |
| `managents flash [--port P] [--image F] [--baud N]` | Write the embedded firmware to a board over USB, about 13 s at 460800 baud, checked against the chip's MD5. Stops the service for the transfer and starts it again. See [ADR-0012](../docs/adr/0012-built-in-flasher.md). |
| `managents demo [--port P] [--hold 6s]` | Cycle through demo screens (every layout, status and edge case, with made-up project names) on the connected displays. |
| `managents version` | Print the version. |

`run`, `demo` and `devices` need the serial port, which the service holds: stop it first
(`managents service stop`, `managents service start` afterwards), or `devices` just reports the port as in use.

## What is detected

| Agent | Source | Status |
|---|---|---|
| Claude Code (terminal and desktop app) | `<config dir>/sessions/<pid>.json`, the live session registry. The config dir is `~/.claude`, or `$CLAUDE_CONFIG_DIR` when set. Only files named `<digits>.json` are read. A record counts only if its pid is running **and** started when the record says (stale files from crashed sessions are ignored). | `busy` → working; a pending permission prompt or question → waiting, and it stays waiting; idle at the prompt → waiting, or error when the last main-thread message is an API error, and either turns idle after 2 h. Context size comes from the last main-thread model call that reports usage (API-error entries have none and are skipped); the limit is 200k, or 1M once a session goes past 200k (force it with `--claude-context`). |
| OpenCode | Running `opencode` processes and their TUI tabs: each open tab is a card, from `$XDG_STATE_HOME/opencode/latest/tui/tabs.json` (default `~/.local/state/opencode/latest/tui/tabs.json`), opened read-only and decoded for session ids only, never the tab titles. A folder whose tabs are not known (OpenCode 1, `tabs.scope: global`, an unreadable state file) is one card, owned by the oldest process there; `opencode serve` is not a session, and the desktop app has no process of its own in the project folder. Status comes from `$XDG_DATA_HOME/opencode/opencode.db`, default `~/.local/share/opencode/opencode.db`, opened read-only: `session_message` of OpenCode 2, or `message` and `part` of OpenCode 1. | Newest step of the tab unfinished (or finished with tool calls, so the turn goes on), or a prompt sent < 90 s ago → working (its age counts from the prompt; a reply written before the process started is not working); the turn's `idle` row ends it; assistant error or a failed turn → error (an interruption is not an error); a tool frozen at `running` for > 6 s → waiting; error and waiting turn idle after 2 h. A tab's subagents count as the tab: the parent's task tool stays running while they work. OpenCode does not store pending permissions, so the 6 s rule cannot tell a long silent command from a permission prompt. A store error is logged and the sessions are still shown. |
| Codex CLI | Running `codex` processes (one card per working directory, owned by the oldest process there; `codex exec`, the background `codex app-server` and the other service subcommands are not sessions). The folder's thread is the newest one in `$CODEX_HOME/state_<N>.sqlite`, default `~/.codex`, opened read-only (not archived, not a subagent's, not run by `codex exec` or `codex mcp-server`); its status comes from the end of the thread's rollout (the same tail as for Claude Code). | `task_started` without its `task_complete` → working (its age counts from the start of the turn; a turn written before the process started is not working); `task_complete` → waiting, or error when it carries an error; `turn_aborted` (an interruption) → waiting; a tool call left without output for > 6 s while no command started during the turn runs in the folder (a child of a `codex` process, the TUI or its app server; a long command is polled by later calls, so the turn is what counts) → waiting, which is how an approval prompt or a question shows; error and waiting turn idle after 2 h. Context size and limit come from the last token count (`last_token_usage` of the model's `model_context_window`). Codex sessions of the IDE extension or the desktop app have no `codex` process of their own and are not shown. |
| ZCode (terminal and desktop app) | Running session processes, one look per working directory: the `zcode-cli` binary, and the desktop app's Electron helpers, whose process title it rewrites to `zcode-cli` (matched by that title, so the app's own helpers and its `zcode-host-local` and MCP services are not sessions; sessions ZCode runs for itself, anywhere under `~/.zcode`, are not either). Every conversation of a folder is a card of its own: `~/.zcode/cli/db/db.sqlite`, opened read-only, records them all, the one written to last first, so several tasks in one project each get a card. A folder whose conversations cannot be read is one waiting card, owned by the oldest process there. | A prompt in `session_input` whose `turn_usage` row has not appeared → working, from the prompt (ZCode writes the row when the turn ends); turn `completed` or `cancelled` (an interruption) → waiting, `error` → error, from the turn's end. ZCode records no close, so a conversation it has not written to for 5 minutes is not shown any more — a working conversation is kept whatever its write age — and nothing goes idle. ZCode stores no context-window size, so its cards have no context bar, and it records no pending approvals: a session blocked on one shows as working until it is answered. |
| Qwen Code | Running `qwen` processes (one card per working directory, owned by the oldest process there). The folder's active conversation is the newest session file under `$QWEN_HOME/projects/<sanitized cwd>/chats/`, default `~/.qwen` — Qwen Code names that directory after the working directory with every non-alphanumeric character turned into `-`, and the file's records carry the working directory, which settles folders whose names collide after sanitizing. The file is read at both ends: the head for the session id, start time and working directory, the tail for the status, like Claude Code's transcripts. A folder whose session file cannot be matched is one waiting card, owned by the process there. | A user prompt without a trailing `turn_result` record → working, from the prompt (a prompt written before the process started belongs to a previous run, and a prompt without its turn that has hung for 2 h goes idle); trailing `turn_result` `completed` or `cancelled` (an interruption) → waiting, `error` → error, from the turn's end; idle after 2 h. Subagent traffic (`isSidechain` records) is not the session's turn and its token use is not counted. Context size and limit come from the newest `usageMetadata` total and `contextWindowSize`. Conversation content — the `message` field, the turn result texts, the title sidecars — is never decoded. |
| Gemini CLI | Running `gemini` processes (one card per working directory, owned by the oldest process there). The folder's project is looked up in `~/.gemini/projects.json` (the working directory → slug registry), falling back to the `.project_root` marker files Gemini CLI leaves in `~/.gemini/tmp/<slug>/`; its active conversation is the newest `session-*.jsonl` in that project's `chats/`, read at both ends like Claude Code's transcripts. A subagent session (`kind: subagent`, kept one level below in `chats/<parent session>/`) gets no card of its own — the parent's card keeps showing the turn. A folder whose project is not registered yet, or whose session file cannot be read, is one waiting card, owned by the process there. Sessions of a sandboxed run (`SANDBOX=sandbox-exec` moves the state to `~/.cache/gemini`) are not found. | Gemini CLI writes no status: the newest message record decides — a user prompt → working, from the prompt (a prompt written before the process started belongs to a previous run, and one without its reply that has hung for 2 h goes idle); a `gemini` reply → waiting, unless its tool calls are still `executing` (→ working) or stuck at `awaiting_approval` (→ waiting, which is how a permission prompt shows; whether that status is persisted before the approval is answered is not guaranteed); an `error` record → error; idle after 2 h. Context size comes from the newest `tokens.total`; Gemini CLI stores no context-window size, so there is no limit. Conversation content — `content`, `displayContent`, tool call arguments and results, thoughts, summaries — is never decoded. |
| pi | Running `pi` processes (one card per working directory, owned by the oldest process there). The folder's active conversation is the newest session file under the pi sessions folder (default `~/.pi/agent/sessions`, moved by `$PI_CODING_AGENT_DIR` or `$PI_CODING_AGENT_SESSION_DIR`), in the subfolder pi names after the working directory (leading slash stripped, `/` `\` `:` turned into `-`, wrapped in `--...--`); the file's header carries the working directory, which settles folders whose names collide after encoding. The file is read at both ends like Claude Code's transcripts: the header for the session id, start time and working directory, the end for the status. pi records no turn state, and its process environment (which would pair sessions directly) is not read. | The newest message entry decides: a user prompt or a tool result → working, from the prompt (an entry written before the process started belongs to a previous run, and a prompt without its reply that has hung for 2 h goes idle); an assistant message stopped to call a tool with no tool result after it → waiting, which is how a permission prompt shows; stopped with `error` → error; stopped otherwise (`stop`, `aborted`, `length`, `deferred`) → waiting; idle after 2 h. Context size comes from the newest assistant `usage.totalTokens`; pi stores no context-window size, so there is no limit. Conversation content — message contents, compaction and branch summaries, tool results — is never decoded. |
| droid (Factory) | Running `droid` processes (one card per working directory, owned by the oldest process there). The folder's active conversation is the newest session file under `<factory home>/sessions/<project key>/`, default `~/.factory`, moved by `$FACTORY_HOME_OVERRIDE` — droid names the project folder after the resolved working directory (a dash, then the path without its leading slash, every slash a dash), and the file's first line carries the working directory, which settles folders whose keys collide. Factory records no status anywhere, so only three things are read: the file's first line (the `session_start` record: session id and working directory), the `<session id>.settings.json` sidecar (its `archivedAt` hides an archived session, whose data is kept) and the file's timestamps. The transcript after the first line — messages, tool results, titles — is never decoded, and the legacy layouts (sessions straight in `sessions/`, the `btw` sessions) are skipped. A folder whose session file cannot be matched is one waiting card, owned by the process there. | The file's last write decides: written < 90 s ago → working (the closest droid gets to a turn in progress; its age counts from the write, and a long silent tool run drops to waiting); quieter → waiting — a finished turn and a permission prompt look exactly alike; untouched for 2 h → idle. A card has no context bar: droid stores no token counts. StartedAt is the file's creation time on macOS, its last write elsewhere. |
| Crush | Running `crush` processes (one card per working directory, owned by the oldest process there). The folder's state lives in a per-project data directory: the one Crush's global registry maps the working directory to (`projects.json` under `$CRUSH_GLOBAL_DATA`, else `$XDG_DATA_HOME`, else `~/.local/share`), else the nearest `.crush` directory at or above it. Its database, `crush.db`, is opened read-only for the project's active session — the newest one, without the special sessions Crush runs for itself (title generation, agent tools) — and for that session's newest message, whose `finished_at` says whether the turn is over. Crush holds a lock file (`crush.lock`, the pid of its process) over the data directory while it runs. A folder without a data directory, database or session yet is one waiting card, owned by the process there. | The lock says whether Crush is alive: a lock whose pid is running and a newest message that is a prompt, or an assistant message without `finished_at`, → working, from the prompt (a message written before the process started belongs to a previous run, and a turn that has hung for 2 h goes idle); the lock running and a finished message → waiting; behind a lock whose pid is gone — a run that crashed — nothing works: it waits, and goes idle after 2 h like everything else. Crush records no turn failure anywhere on disk, so an error cannot be told from a finished turn, and a permission prompt is not distinguishable from a working turn. Context size comes from the session's `prompt_tokens` and `completion_tokens`; Crush stores no context-window size, so there is no limit. Conversation content — message parts, file snapshots, todos, titles — is never decoded. |
| Goose (Block) | Running `goose` processes (one card per working directory, owned by the oldest process there). The folder's active conversation is the newest session Goose keeps for it in its sessions database — macOS: `~/Library/Application Support/Block/goose/sessions.db`, elsewhere: `$XDG_DATA_HOME/goose/sessions.db` (default `~/.local/share`), `$GOOSE_PATH_ROOT` moves the whole store to `<root>/data` — opened read-only, the session row named by its `working_dir` column (the real path, symlinks resolved) and updated in place on every turn. Goose records no status anywhere, so only the session row's id, timestamps and token counts and the newest message's role and time are read. A folder without a session yet is one waiting card, owned by the process there. | The role of the session's newest message decides: a user prompt without its reply → working, from the prompt (a message written before the process started belongs to a previous run, and a prompt without its reply that has hung for 2 h goes idle); an assistant message → waiting; idle after 2 h. Goose writes neither a turn failure nor a permission prompt to disk, so an error cannot be told from a finished turn and a prompt can as well be a permission question as a task still running. Context size comes from the session's `total_tokens`; Goose stores no context-window size, so there is no limit. Archived sessions (`archived_at`) are hidden. Conversation content — message contents, recipes, session names and descriptions — is never decoded. |
| Amp (Sourcegraph) | The local thread mirror, `<data dir>/threads/T-<id>.json` — `$XDG_DATA_HOME/amp/threads`, default `~/.local/share` — one JSON document per thread, rewritten in place as the thread runs and parsed with a filtered struct: the thread's id and creation, each message's role, its state (`streaming`/`complete` and the stop reason), the newest content block's tool-run status and the newest assistant turn's `totalInputTokens`. The mirror is undocumented and not guaranteed to be there: a thread it does not carry (the desktop app, an orb or a runner run) gets no card, and a thread whose working directory it does not name gets none either — the directory lives in the opaque `env` object captured at the thread's start, which key carries it could not be confirmed, so every plausible one is read and only an absolute path is trusted. | The statuses are explicit: a tool result still `queued` or `in-progress` → working, `blocked-on-user` or `rejected-by-user` → waiting — kept for as long as it takes, the user's answer being the next write of the mirror; a `done` or `cancelled` run, or a `complete` message stopped for good → waiting; a failed run, or a complete message stopped on an `error` → error. A thread is a card while amp writes it: one quiet for 5 minutes is closed or abandoned and is not shown any more (like ZCode's conversations, so nothing goes idle), a running one is kept whatever its write age — for 2 h, after which a run silent that long is one that died mid-turn — and a blocked one is kept until answered. A card's age counts from the mirror's last write; the mirror carries no per-message timestamps. Context size comes from the newest assistant `totalInputTokens` (no limit: amp stores none). Whether an `amp` process is still running is not checked. Conversation content — text, thinking, tool calls and their results, titles — is never decoded. |
| Oh My Pi (omp) | Running `omp` processes (one card per working directory, owned by the oldest process there). omp is pi-derived and writes the same session logs, read through the shared pi-format reader, in a config tree of its own: the default agent dir (`<$PI_CONFIG_DIR or ~/.omp>/agent`, moved by `$PI_CODING_AGENT_DIR`) and every named profile under `<config root>/profiles/<name>/agent` — all scanned, whichever profile a process runs under (that lives in its environment, which is not read). On Linux and macOS an `$XDG_DATA_HOME` whose `omp` folder exists takes over, the `agent/` prefix flattened away (`$XDG_DATA_HOME/omp/sessions`, a profile's under `$XDG_DATA_HOME/omp/profiles/<name>/sessions`): omp's sign that `omp config migrate` has run; otherwise the agent dir holds the sessions. The folder is named after the working directory relative to the OS temp root (checked first) or to home — `-work-payments-api`, `-tmp-scratch-app` — or, outside both, pi's absolute `--work-payments-api--`, which the runs before omp moved its folders used everywhere and which stays a candidate; the file's header carries the working directory (under either of its macOS spellings), which settles folders whose names collide. The file is read at both ends: the header (behind omp's fixed-width title slot) for the session id, start time and working directory, the end for the status. | The newest message entry decides, as for pi: a user prompt or a tool result → working, from the prompt (an entry written before the process started belongs to a previous run, and a prompt without its reply that has hung for 2 h goes idle); an assistant message stopped to call a tool with no tool result after it → waiting, which is how a permission prompt shows; stopped with `error` → error; stopped otherwise (`stop`, `toolUse`, `aborted`, `length`) → waiting; idle after 2 h. An entry written off the active branch (`activeLeafId`) does not decide — omp replays it against the recorded leaf. Context size comes from the newest assistant `usage.totalTokens`; omp stores no context-window size, so there is no limit. Sessions opened with `--session-dir` elsewhere, and the short-lived folder names of omp 17.2.5–17.2.8 (reverted upstream), are not found. Conversation content — message contents, title-slot titles, compaction and branch summaries, tool results — is never decoded. |

Cards are ordered by activity: working sessions first (in start order, so they don't swap places), then everything
else with the most recent status change first. Agents left waiting or idle for a long time sink to the later pages.
Names are the folder name, `parent/name` when two folders share a name, and `name #1`, `name #2` for several
sessions in the same folder.

## Discovery

- Only USB serial ports behind these bridges are probed: WCH CH340 and CH9102 (VID `1A86`), Silicon Labs CP210x
  (`10C4`), Espressif native USB (`303A`) and FTDI (`0403`). Anything else needs `--port`. On macOS only `/dev/cu.*`
  is used.
- A port that does not answer the handshake is probed when it appears, again 10 s later, and 60 s after that; then
  it is left alone until it is replugged. A `--port` port is retried every 60 s. A port in use by another program is
  retried on every 2 s pass.
- Discovery runs in the background: connected displays get a frame at least every 2 s whatever the probing does (the
  display's link timeout is 6 s).
- One helper per display: the port is opened exclusively, so a second helper (or `demo`, or a second user's service)
  gets "busy".

## The background service

`managents service install` registers `managents run` to start at login and restart if it exits
([ADR-0010](../docs/adr/0010-always-on-user-service.md)). Run it again after an update to replace the old one.

| | macOS | Linux |
|---|---|---|
| Unit | LaunchAgent `com.github.tonylook.managents`, `~/Library/LaunchAgents/com.github.tonylook.managents.plist` | systemd user unit `managents.service`, in `~/.config/systemd/user/` |
| Log | `~/Library/Logs/managents.log` (and `.1`), also readable in Console.app | `journalctl --user -u managents` |
| Windows | no service yet: Task Scheduler → "At log on" → `managents.exe run` | |

`managents service status` shows whether it runs, any warnings and the latest log lines. `uninstall` stops the
service and removes its file and logs. Your user must be allowed to open serial ports on Linux (group `dialout` or
`uucp`). The binary must live somewhere permanent (`~/.local/bin`): `install` refuses temporary folders, `go run`
builds, and on macOS `~/Desktop`, `~/Documents` and `~/Downloads`.

### What the log says

Lines worth knowing (the exact text):

| Level | Message |
|---|---|
| info | `display connected` (port, board, firmware, size) and `display disconnected` |
| info, once per busy episode | `serial port in use by another program; if it is the managents service: managents service stop` |
| info, once per plug-in | `serial port did not answer as a managents display; new board? run: managents flash` |
| warn | `display firmware is out of date; update it with: managents flash` (with the firmware and the minimum) |
| info | `display speaks a newer protocol than this helper; update the helper` |
| warn | `listing serial ports failed` (once per distinct error) |

## Privacy

The helper reads the session registry, the **end** of each open session's transcript (the last 256 KiB, growing to
at most 4 MiB only when no token usage is found there), OpenCode's database read-only, Codex's thread list read-only
(folder and rollout path only) with the same tail of each thread's rollout, ZCode's database read-only (ids,
statuses and timestamps of prompts and turns only), and the process list. A Claude Code
transcript is decoded for four things only: entry type, sidechain flag, API-error flag and token counts; a Codex
rollout for entry and event types, timestamps, whether a turn ended in an error, and token counts. Conversation
text is never decoded, stored, logged or sent. The frame on the USB cable carries the folder name, status, age and
context token counts, nothing else (no directory paths). No network connections. Canary tests
(`TestConversationContentNeverLeaks` in every detector package) enforce it.

## Layout

See [docs/architecture.md](../docs/architecture.md#helper). Tests: `go test -race ./...` (or `make test-helper`): no
agents, ports or displays needed; the protocol tests check the shared fixtures in [`../protocol`](../protocol)
against the schema. `go tool staticcheck ./...` and `go tool govulncheck ./...` are pinned in `go.mod`.
